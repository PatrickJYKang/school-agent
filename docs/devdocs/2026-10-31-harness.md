# Development journal: agent harness design

Date: 2026-10-31. Status: side-conversation research and design considerations.
This note records proposals, not newly implemented capabilities or an approved
expansion of the pilot.

## Source

Patrick shared [LunarResearcher's post on harness engineering](https://x.com/LunarResearcher/status/2096570562625655088).
The original could not be loaded directly. The discussion used a
[Chinese-language mirrored version](https://www.jxxy.net/ai/articles/LunarResearcher-2096570562625655088/),
so the original wording was not independently verified.

The article argues that reliable agents need infrastructure around the model:
relevant context, controlled tools, durable state, verification and bounded
recovery. It also recommends adding complexity in response to observed failures
and removing safeguards or orchestration that no longer justify their cost.

## Implications for this project

These are our applications of the article, not a specification taken from it.
Describe the execution contract alongside the database schema in the
[backend design](../backend.md). Reuse LibreChat's existing mechanisms wherever
they fit; a runtime concept does not automatically require a new collection.

- **Authorization:** The model requests an action; the backend independently
  authorizes it. Define how institution policy, user identity, source access and
  conversation restrictions are checked on every call, including existing chats.
  Read-only Microsoft access must be enforced through credentials and tool
  operations. Model instructions cannot grant permission.
- **Context:** Retrieve relevant assignments, messages or documents on demand.
  Define how sources are discovered and admitted without loading or indexing an
  entire account. Retrieved source text is untrusted content, not an instruction
  or permission grant.
- **Execution and recovery:** Define cancellation, time and cost limits, bounded
  retries, and behavior when connections expire or retrieval fails. Distinguish
  denied access, unavailable sources, empty results and partial reads. Avoid
  repeating an unchanged failed operation indefinitely.
- **Evidence:** Preserve useful source references and retrieval context. Answers
  should disclose incomplete reads and unavailable information. Verification can
  establish that retrieval succeeded; it does not by itself prove that an essay,
  explanation or interpretation is correct.
- **Persistence:** Specify what survives between turns and which messages, tool
  results, files and execution state are stored. Define retention and access for
  each copy rather than treating the conversation transcript as a complete
  execution-state design.

## School-specific qualifications

**Reading can expose sensitive information.** Read-only access protects source
records from modification; confidentiality also depends on disclosure to models,
other tools and storage. Email or document contents entering a public web query
is an example of a boundary that requires backend enforcement.

**Tracing needs restraint.** Recording every tool input and output could create
another repository of private school content. Prefer necessary operational
metadata, safe error codes and source references, with access and retention
rules. Existing chat/tool content storage and a minimal audit trail are different
things. Do not store hidden model reasoning as an audit requirement.

**Ordinary conversations should stay lightweight.** A student asking for an
explanation does not need a formal task contract, a persistent task board or a
separate verification agent. Introduce explicit task state or stronger checks
where a demonstrated workflow needs them.

## Scope and follow-through

Use this note when reviewing the backend design's authorization, context,
execution, evidence and persistence contracts. Map each concern to an existing
mechanism, a concrete gap or a deferred requirement before implementing it.
The [Microsoft access plan](../microsoft.md) remains the reference for its
read-only scope and confidentiality requirements.

This discussion does not add browser/terminal execution, multi-agent
orchestration, folder merging or collaborative document editing to the pilot.
The only change made for this journal request is saving this note.
